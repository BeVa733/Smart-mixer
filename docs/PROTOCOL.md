# Smart Mixer: протокол обмена v1

## Статус реализации

Реализован общий кодировщик и потоковый парсер в
[`SmartMixerProtocol`](../shared/SmartMixerProtocol/src/SmartMixerProtocol.h).
Формат кадра и проверки ниже покрыты тестами на компьютере. Модуль пока не
подключён к UART или исполнительным механизмам.

Сессии, команды, повторы, heartbeat и остановка в следующих разделах описывают
контракт будущей реализации. Они ещё не обеспечиваются текущими прошивками.
Этапы и критерии приёмки: [PROTOCOL_IMPLEMENTATION.md](PROTOCOL_IMPLEMENTATION.md).

## Ответственность

ESP32 отвечает за LVGL, рецепты и последовательность операций. Он запрашивает
действие и показывает подтверждённое Arduino состояние.

Arduino отвечает за физическое выполнение, проверку пределов, концевик,
аппаратную калибровку в EEPROM и остановку оборудования. Только Arduino решает,
можно ли начать исполнительную операцию. ACK не означает завершение действия.

USB-команды, энкодер и UART должны использовать один исполнитель с явным
арбитражем: два источника не могут параллельно управлять одним механизмом.
Текстовые USB-команды остаются диагностическим интерфейсом и не становятся
форматом межконтроллерного протокола.

## Физический канал

Аппаратный UART, 19200 бод, 8N1, без flow control. Начальная скорость выбрана
для проверки уже запланированного BSS138 на коротких проводах.
Переход на другую скорость требует одинаковой конфигурации обеих сторон и
повторных испытаний. Распиновка и конфликт CH340 описаны в
[CONNECTIONS.md](CONNECTIONS.md).

## Формат кадра: реализовано

```text
@1|session|id|TYPE|NAME|arguments*HHHH\n
```

На линии `\n` означает один байт LF `0x0A`, а не два печатных символа.
CRLF не принимается. В кадрах нет NUL, пробелов, русского текста или JSON.

| Поле | Правило |
|---|---|
| `@` | Начало нового кандидата кадра; также сбрасывает незавершённый кадр |
| `1` | Единственная поддерживаемая версия |
| `session` | Десятичный uint32, `0..4294967295` |
| `id` | Десятичный uint32, `1..4294967295`; ноль запрещён |
| `TYPE` | Ровно `CMD`, `ACK`, `DONE`, `ERROR`, `STATUS` или `EVENT` |
| `NAME` | 1–24 символа, первый `A..Z`, остальные `A..Z`, `0..9`, `_` |
| `arguments` | 0–128 символов из `A..Z a..z 0..9 _ , = . + -` |
| `HHHH` | Ровно 4 шестнадцатеричных символа `0..9 A..F` |

Числа заголовка не содержат знак или ведущие нули, кроме самого `0`.
Разделителей `|` строго пять. Пустой arguments сохраняет последний `|`.
Максимальная длина на линии — 192 байта, включая `@` и LF.

CRC-16/CCITT-FALSE: polynomial `0x1021`, initial `0xFFFF`, refin/refout false,
xorout `0x0000`. Считается по ASCII-байтам от `1` до последнего байта arguments
включительно, с разделителями `|`; `@`, `*`, четыре цифры CRC и LF исключены.
Эталон: CRC строки `123456789` равна `29B1`.

Независимо рассчитанные кадры:

```text
@1|0|1|CMD|HELLO|*9723
@1|42|17|CMD|DOSE|pump=2,volume_ul=50000*79A5
@1|42|17|ACK|DOSE|*8982
@1|42|17|DONE|DOSE|elapsed_ms=20000*1E99
```

Каждая показанная строка завершается LF при передаче.

Поведение парсера:

- Байты вне кадра игнорируются до `@`.
- Новый `@` начинает кадр заново; увеличивается счётчик resync.
- Управляющий или не-ASCII байт внутри кадра сбрасывает кандидат.
- При переполнении кадр отбрасывается; остаток игнорируется до нового `@`.
- Незавершённый кадр истекает через 250 мс от `@`, даже если байты продолжают
  поступать. Расчёт времени учитывает переполнение 32-битного `millis()`.
- Сначала проверяется CRC, затем структура и поля. Выходной Packet изменяется
  только после полной успешной проверки.
- Ошибки возвращаются вызывающему коду и считаются локально. Парсер ничего
  не отправляет в ответ и не вызывает исполнительные функции.

`arguments` пока проверяется только по длине и допустимым символам. Проверка
`key=value`, обязательных ключей, единиц, диапазонов и семантики команд будет
в отдельном обработчике после парсера. Валидная CRC сама по себе не даёт
права выполнить команду.

## Контракт сессий: к реализации

1. ESP32 отправляет HELLO с session=0.
2. Arduino сообщает версию, идентификатор своей загрузки и возможности.
3. Стороны устанавливают свежую ненулевую сессию, не повторяемую между
   перезапусками. Точный обмен и способ получения идентификаторов закрепляются
   перед реализацией менеджера сессий.
4. ESP32 получает полный STATUS. Только затем открывается управление.

Session=0 разрешена только для начального обмена. Кадры старой сессии не
выполняются. Новая сессия не перехватывает активную операцию молча: сначала
действие должно завершиться или быть остановлено. Несовместимая версия
блокирует управление и отображается на экране.

После перезапуска нет автоматического продолжения рецепта или повторного
налива. Положение после отключения/сброса механики считается недостоверным до
homing. После потери состояния операции результат может быть UNKNOWN;
отсутствие результата не означает, что жидкость не была подана.

## Классы сообщений и операции: к реализации

| TYPE | Смысл |
|---|---|
| CMD | Запрос операции или служебной команды |
| ACK | Команда проверена и зарегистрирована; выполнение ещё не завершено |
| DONE | Успешное завершение команды с результатом |
| ERROR | Отказ в приёме либо неуспешное завершение |
| STATUS | Снимок состояния |
| EVENT | Асинхронное изменение состояния или ошибка |

Для ответов используется ID исходного запроса. Самостоятельные события имеют
отдельную возрастающую последовательность ID отправителя; пространство
идентификаторов разделяется направлением и TYPE, чтобы EVENT не путать с
ответом на CMD.

Первая интеграция: HELLO, PING, GET_STATUS, GET_OPERATION, HEARTBEAT, STOP.
После асинхронного исполнителя: HOME, MOVE, DOSE, PRIME и калибровка.

Одна исполнительная операция одновременно. Конфликтующая получает BUSY;
STOP, heartbeat и запросы состояния продолжают обслуживаться. Автоматической
очереди исполнительных команд на Arduino нет. Рецепт хранит очередь на ESP32.

Единицы: объём — целые микролитры, время — миллисекунды, положение и движение —
знаковые микрошаговые импульсы STEP. Допустимые диапазоны закрепляются для
каждой команды. Дозирование по времени сообщает расчётный результат, а не
подтверждённый датчиком физический объём.

## Повторы и ошибки: к реализации

ESP32 назначает возрастающий ID каждой новой команде в пределах сессии.
Повтор использует прежние ID и параметры. При исчерпании uint32 требуется
новая сессия в состоянии простоя, без заворачивания ID в текущей сессии.

Arduino хранит активную операцию и ограниченную историю терминальных ответов.
Повтор активной команды возвращает её состояние, повтор завершённой —
сохранённый результат. Тот же ID с другим запросом отклоняется как ID_CONFLICT.
Слишком старый ID вне истории отклоняется как STALE_ID; его нельзя считать
новой командой. Окно истории и алгоритм сравнения закрепляются в этапе 7.

После ACK потеря DONE разрешается через GET_OPERATION, без повторного запуска.
После перезапуска неизвестное дозирование нельзя повторять автоматически.

Коды ошибок: BUSY, NOT_HOMED, NOT_CALIBRATED, OUT_OF_RANGE, LIMIT_REACHED,
HOME_TIMEOUT, LINK_LOST, CANCELLED, ID_CONFLICT, STALE_ID, UNKNOWN_OPERATION,
BAD_ARGUMENTS, WRONG_SESSION. Тексты для человека формирует ESP32.

Начальные параметры для измерений на стенде: heartbeat 500 мс, разрыв после
2000 мс без валидного контрольного обмена, ожидание ACK 500 мс, не более двух
повторов с прежним ID. Тайм-аут выполнения задаётся для каждой операции.

STOP обрабатывается с приоритетом, включая homing и движение. Насосы
выключаются, генерация новых STEP прекращается. Остановленная операция
получает CANCELLED, STOP — отдельное подтверждение завершения. Поведение EN
двигателя определяется удержанием вертикальной нагрузки, а не отключается
безусловно. При потере связи локальная защита Arduino выполняет ту же
остановку. Время реакции проверяется измерением на стенде.

## Правила исполнения и LVGL

Блокирующие homeUp(), moveActuator() и чтение USB-строки нужно заменить перед
удалённым управлением механизмами. Опрос UART, watchdog связи и обновление
насосов продолжаются во всех состояниях, включая HOMING и FAULT.

На ESP32 callback кнопки только ставит запрос в ограниченную очередь. UART
обновляет модель состояния; объекты LVGL меняет только контекст UI. ISR и
UART-callback не вызывают LVGL и не изменяют framebuffer. Ожидание ACK не
останавливает lv_timer_handler(). Сохраняются оба RGB565 framebuffer,
FULL-render, bounce buffers и VSYNC из [правил дисплея](../display_controller/DISPLAY_LVGL_RULES.md).
